# Personas

The home of the operator's AI agents: each with its own name, picture, personality and memory, taking part in the operator's apps the way a person does.

For the operator, who gives each agent its name and rights, and for the people who meet his agents in his apps.

## What runs now

The runner. Each agent signs in to the realm as itself, with its own client, and for every app it may reach that listens it keeps one subscription open on the app's MCP endpoint and reads its standing whenever the app says something changed. When it is invited to a call it accepts, and it appears there under the name the realm gives it, with the AI mark. It never leaves on its own; it is removed with its seat, its lease or its client. In a call it reads every line from its join on, takes what was said before a restart or during a pause as read, and answers once a line said after names it, as a whole word in any case, with one model turn through the operator's LiteLLM gateway; it never takes its own line as addressed to it. With a `[memory]` table it keeps every line it reads, verbatim, in a Postgres of its own, and when he is addressed he is also told what was said in his other visits of the day: back in a call four hours after he left it, he knows what was said there.

Which apps an agent can use is the realm's group membership, not this configuration. When the realm or an app refuses an agent (a disabled client, a missing group), that agent's loop for that app is suspended and logged once, and it resumes when the refusal ends, without a restart.

## Run it

Install with `uv sync`, point `PERSONAS_CONFIG` at a TOML file and start `personas`. The file holds the realm's token endpoint, the absolute path `ready_file`, the apps (MCP URL and scope) and the agents (client id and the path of the file holding its client secret). An app that lets its agents answer also lists the tools their turns may call as `tools`, with `max_tool_calls`, the most calls one turn makes in that app; the two are set together. A call past an app's own bound is answered with an error and the model may go on, but the turn's total is the sum over its apps and counts the refused calls too, so a model that keeps calling past a bound can spend the total and end the turn without its `say`. An app that serves tools only sets `listens = false` and `tools`: no loop runs for it, and its tools join the turns of the other apps, each request in a session of its own under a token for its own scope. Its `call_seconds` (default 30) bounds each such request, a relayed call or an opening, so keep it below the persona's `maxDurationSeconds`; nothing refuses a larger value. A tool name may not be shared with a tools-only app, and at least one app must listen. Then the file needs the `[gateway]` table, which is agents' `AgentConfig` (`backend`, `api_group` and `[gateway.gateway]` with `origin`, `key_file` and, for HTTPS, `ca_file`), and every agent a `persona_file`: the absolute path of its agent file `<name>.md`, whose prompt is the agent's character, and, only when the operator wants one, the turn-rate cap `max_turns` (a positive integer) and `turn_period_seconds` (a positive number), set together: at most `max_turns` turns start in any `turn_period_seconds`, counted across all the apps of the agent and from the runner's start. A line addressed to the agent over the cap is skipped, logged once as `capped` and never answered later. The cap is off unless both fields are set; the person's budget at the gateway and the off switches (the invitation, its removal and the person's permission to be heard) bound an agent then. The agent file names no tools and no call bound and offers the role `user`, under which a turn runs. The token's `agent_name` claim is the name a line must carry to address the agent. `src/personas/config.py` owns its fields and what is refused at start; the runner stops with the field named, never a secret.

The optional `[memory]` table names the database that keeps every line the agents read: `host`, `port`, `dbname`, `user`, `password_file` (the absolute path of the file holding the password), `write_seconds`, the bound on one write or read against a database that answers (default 2, `inf` for none; a connection that goes dark in the middle of a write is given up only after the driver's own cancel wait, about ten seconds more). A large or absent bound has a cost: the write runs inside the listen's deadline, so a database that goes dark then holds that loop until the deadline, the app is backed off as a network failure, the turn already running is cancelled with its answer, and no `store_failed` is logged; a bound from about 40 seconds on carries the same risk. Under `inf`, `personas migrate` hands the driver no connect timeout, so the driver's own default bounds the connect; under any bound, a database that stops answering after the connect holds it. The runner opens no connection at start and starts also when the database cannot be reached: it logs `store_failed` with the code `store_unreachable` or `store_timeout` once, answers as it always does, and logs `store_resumed` when a write or read succeeds again; a schema that is behind ends the runner. `personas migrate` brings the schema to its head and needs the table; when it cannot reach the database or meets a database error it prints `personas: memory:` with the code and exits non-zero; run it before the runner starts and after every release. `personas memory list` prints, tab-separated under a header, one row per visit (agent's client id, app, place, generation, the number of lines kept, and the first and the last time a line of it was first read), never a line's text or a speaker's name; `--agent <client id>` narrows it to one agent. `personas memory erase --agent <client id>` deletes every line that agent keeps, also of an agent no longer configured, and `personas memory erase --all` every line of every agent; it prints the number deleted, 0 included, and keeps the schema. Exactly one of the two is given, or the command prints its usage and deletes nothing. Both commands need the table and fail like `personas migrate`; a schema behind its head refuses them. An erase removes what was kept up to that moment: an agent in a call keeps that call's window again at its next read, because the app still holds it, so erase for good after the agent has left or with the runner stopped. Reading a window again keeps each line once, with the time of its first read. `today_hours` (default 24, `inf` for every kept line) and `today_bytes` (default 32768) set what a turn is told of the day: the lines of the agent's other visits first read within `today_hours`, visit by visit in the order they happened, each with the minutes since its first line, the speakers' names and his own lines marked; past `today_bytes` of names and text the oldest are left out, and the turn is told that they were. A read that fails or outlasts `write_seconds` is logged as `store_failed` like a write, and the turn answers without the day.

The runner opens no port. It removes `ready_file` at start, so a marker left by an earlier run never counts, and creates it the first time any loop's read of its standing answers: the start worked, the realm gave a token and an app accepted it. A refused token, a suspended loop, a network failure or a 5xx does not create it, so a wrong secret or URL shows as not ready. The marker stays afterwards; a later suspension or outage is in the log. If the file cannot be removed or created, the runner exits non-zero naming the path. The platform's readiness probe is `test -e <ready_file>`.

The runner stops on SIGTERM with exit code 0 and needs no init, in the image or the deployment. The deployment supplies the configuration, the persona files included, and the secret files; the image holds none of them.

The commands for working on the runner are in [AGENTS.md](AGENTS.md).

## Release it

The image is the runner's release. The operator dispatches the `Release` workflow (`.github/workflows/release.yml`) on `main` with the version as `YYYY.MM.DD.N`, for example `2026.11.08.1`. Quality's gate refuses a commit whose checks are not green, the image is pushed to GHCR with an attestation, and then the tag `v<version>` is created. The image holds no configuration; `PERSONAS_CONFIG` and the secret files come from the deployment. An AI agent dispatches a release only on the operator's explicit yes for that one version. [quality's release path](https://github.com/overnightworks/quality/blob/v0.10.0/docs/release.md) owns the rules.
